## 2. 已确认的根因与修复

### 2.1 哈希碰撞被误认为可靠词法证据

原链路将 token 映射到 2048 个稀疏桶。无共同 token 的内容也能因碰撞超过 0.17 的信任阈值。例如合成集中，账单负责人问题误取 Redis 过期设置；中文会话时长问题误取模块风格偏好。存在“可信词法”结果后，语义候选整体不进入最终候选池，错误不只是多返回一条，而是可能阻断正确答案。

修复：词法信任、未知上下文扩展和相对阈值比较同时要求真实的正文词项或规范 key/节点/别名支持。利用现有 BM25 词项摘要，扣除纯 key 命名空间贡献；保留精确 key、空格化 key、节点别名。不改索引格式，不降低阈值，不打开未选中的正文。

边界：**词项相关不等于问题已有答案**。关于编辑器订阅价格的问题仍可能命中主题偏好，这不是哈希碰撞，不能宣称此次已解决所有误召回。

### 2.2 评测无法表达正确拒答

原格式要求 `expected_keys` 非空，无法正式标记“没有答案”。同时“命中任一目标”不等于“取全所有相关信息”，容易高估多条记忆覆盖。

修复：

- 明确负例：`expect_empty: true` 且 `expected_keys: []`；主结果和关联都必须为空。
- 正例指标与负例分母分离，新增拒答率和相关标签 Recall@K；只有负例时正例指标为 `null`，不伪造 100%。
- 保持已有逐例硬门禁，不以平均分掩盖失败。
- 拒绝布尔值、小数、字符串型排名参数；v3 在加载模型前拒绝超过 20 的排名上限。旧格式的 64 上限仍兼容旧评测器。
- P95 使用 nearest-rank；明确 `cold` 只统计 reader 构造，不冒充首次查询耗时。
- CLI 新增显式 `--ranking-only`，默认仍检查来源，输出标记证据适用范围。

### 2.3 每次查询重复做派生工作

直接 v3 reader 原有 3 次 Git 子进程；Service 路径为 4 次。v3 前后已校验快照，中间旧词法入口又查一次 HEAD；密集矩阵也逐次重建。

修复：在 v3 前后校验内部调用纯 pointer 排序，旧公开词法入口仍自带新鲜度校验；密集矩阵按 reader 复用。直接 reader Git 次数 3 降至 2，Service 路径 4 降至 3。

保留：前后 store 校验、Active/正文哈希/身份校验、每请求来源检查、作用域规则。没有跨请求缓存来源新鲜度，也没有修改 Service 的索引文件缓存策略。

### 3.2 固定合成集

- 精确 key：16/16，前后相同。
- 自然词查询：16/16，前后相同。

这是小规模、针对已知机制的回归证据，不是总体准确率估计。

### 3.3 性能

同进程载入原始代码快照与候选版本，同索引、同模型；交替先后顺序，4 对预热后统计 30 对查询。性能采样固定使用 10 个历史查询；质量评测则覆盖全部查询，不能混淆两者。

- 词法 P50：72.62ms 至 52.33ms；P95：77.85ms 至 57.80ms。
- 混合 P50：95.50ms 至 66.87ms；P95：100.79ms 至 70.97ms，降低约 **29.6%**。
- 此性能对照中，返回 ID、完整正文和 pointer 分数字段一致。
- 以上是本机配对实验，不是服务 SLA；未将全部收益归因于某一个优化。

初始规模探针覆盖 16/64/256 条合成记忆：索引约 121KB/459KB/1.79MB，重建约 0.44/1.66/8.91 秒。没有对万级记忆作容量承诺，也没有由这些数据推出“必须换向量数据库”。

## 4. 对整体设计的判断与下一步

### 保留现有真相层与审批边界

Git 规范记忆、Pending/Active 分离、精确批次确认、来源绑定、显式维护与恢复流程值得保留。此次阅读和测试没有提供重写它们的证据。检索分数不能决定事实真伪、替代审批，或自动清理记忆。

派生索引只负责查找。实验性知识图谱、技能推荐继续与主 recall 分开，不能因模块已经存在就自动并入生产链路。

### 优先级 1：把“相关”与“足以回答”分开

剩余合成价格问题证明，主题相近不是答案充分。建议下一轮建立查询意图、必要条件、拒答标注，单独评估“看似相关但不回答”的硬负例。保留精确 key 优先，但对非精确词法结果研究有条件的语义补充，而不是出现任一词法命中就排斥全部语义候选。

验收：新冻结盲测中降低错误答案率，同时保持已有精确 key、作用域、拒答和来源保护。不能通过统一降低 0.50 语义阈值解决；实际剩余失败中既有低于阈值，也有高分但排名不合要求的情况。

### 优先级 2：关联边需要查询适用条件

禁止关联案例来自显式 `related_node` 一跳扩展，并非“没有边”或跨项目泄漏。**图上相关不保证本次问题需要返回。** 建议为关联扩展增加查询/任务适用条件或独立相关性门禁，不将全部邻居默认当答案。

验收：现有 5 个关联正例继续通过，禁止关联归零；不能用关闭所有关联获得虚假的通过。关系与条件的结构改动需单独讨论，不在此次静默修改。

### 优先级 3：来源健康与检索质量分开报告

真实记忆存在外部项目源；ranking-only 高分不能代表当前可用。建议提供来源覆盖、过期、不可达、需复审的独立统计，并在获准访问来源后再做 current-use 验收。历史经验可以带警示保留，当前事实不能因召回得分高而绕过来源门禁。

### 优先级 4：以规模实测决定存储优化

当前证据更支持减少重复解析、派生矩阵和 Git 开销，而非换向量数据库。Service 每次读取完整索引 JSON 是下一项可测成本，但缓存必须处理外部索引替换、HEAD 变化、模型变化和并发读取；本轮没有为省时引入不完整缓存。

先补 1K/10K 规模的构建时间、峰值内存、冷启动和正文读取量，再决定紧凑索引或专用向量存储。上下文字符预览继续不等同于模型 token 总预算。
