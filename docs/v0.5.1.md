# v0.5.1 release notes

[简体中文](zh-CN/v0.5.1.md) · [Home](../README.md)

v0.5.1 fixes interrupted maintenance and request-state recovery. The daily MCP tools remain
`start`, `recall`, and `upload`. TEAM mode still requires exact Owner confirmation.

## Recovery and request state

A maintenance transaction whose data changes finished can complete its remaining cleanup after
a legitimate Git-only administration command changes HEAD. Journal seals and target/staging bytes
are still checked. Unfinished preparation or application retains its HEAD guard and blocks further
mutations. Completed cleanup does not replay the data operation.

Archived source bytes remain unchanged. Reading or purging an archive checks its identity against
the request receipt. Reads carry the receipt's lifecycle proof into current-state reconciliation;
purge cannot remove the archive when those identities disagree. A reverted approval produces
`COMMIT_NOT_CURRENT`, including when the original hot upload writeback failed. Proof comes from the
current HEAD's Git ancestry, not an uncommitted claim. Modern request receipts also check the upload
ID recorded in the approval. Reverted requests do not create a new candidate merely because they
are reviewed again. Normal deactivation and replacement return `COMMITTED_NOT_ACTIVE`.

Approval and source revocation now share precise rollback. A failed, uncommitted operation restores
only its declared files. It does not restore unrelated worktree files or undo a successful commit.

## Maintenance cost and diagnostics

Preparing a plan takes one full inventory. Applying it takes another fresh inventory and reuses that
result internally, retaining exact before/after verification and recovery journals. Previously these
operations took two and three full inventories respectively. Historical lookup is shared across
Pending batches during each operation, rather than launching a Git history query for every batch.

This reduces repeated work, not inventory size: `--limit` bounds selected targets, not scanned files.
Cooperative writes still wait on operation/store locks. Recall remains available; this is not a
short-lock implementation. The shared history walk is bounded and reports `APPROVAL_HISTORY_LIMIT`
if operator review is needed, rather than guessing whether an approval occurred.

A missing recovery transaction returns `TRANSACTION_NOT_FOUND`. An interrupted raw-event write
leaves a cheap `RECONCILIATION_RECOMMENDED` health signal. Explicit maintenance compares reserved
and physical counts while retaining monotonic event sequence IDs. The routine signal is metadata-only;
it does not certify that no older file drift exists. Nothing is automatically deleted or reconciled.

## Upgrade

Install the pinned version in the tool environment, then restart its stdio process. Keep the memory
store separate. Old archives and journals are not rewritten on upgrade. Generate a fresh maintenance
plan before executing a previously unexecuted plan; older plans may no longer match the current fields.
Use the [maintenance guide](maintenance.md) for an interrupted transaction rather than deleting its journal.

This release does not enable backups, personal mode, cloud sync, new MCP privileges, or new retrieval
weights. A custom gateway using a different protocol needs separate adapter acceptance; updating
this package alone does not update or certify every client.
