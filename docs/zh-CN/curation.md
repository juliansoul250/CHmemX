# 集中策展与冲突处理

[文档目录](README.md) | [English](../curation.md)

来源工具只有上传权限。集中策展者负责所有正常的永久记忆写入。

## 状态边界

| 状态 | 是否可召回 | 含义 |
|---|---:|---|
| Upload / `PENDING_CURATION` | 否 | 来源 Agent 提交的原始材料 |
| Candidate / Pending Batch | 否 | 已整理但尚未得到 Owner 精确确认 |
| Quarantine | 否 | 命中秘密、嵌入指令或无效来源 |
| Rejected | 否 | Schema、范围或治理规则不通过 |
| Active | 是 | 已通过完整审阅并原子提交到 Git |
| Superseded | 否 | 被新 Active 记录替代的历史值 |

时间较新不代表内容正确。策展者不能按时间戳自动选择真值。

## 一次策展运行

策展者按以下顺序处理上传包：

1. 校验 Schema、Agent ID、Export ID、来源路径、哈希和项目绑定。
2. 扫描秘密、凭据、私钥、Token 和嵌入式越权指令。
3. 计算 Canonical Identity，并在本批上传和当前 Active Memory 中查重。
4. 合并正文与字段完全相同的候选，同时在报告中保留全部来源。
5. 阻止同一 Identity 的不同值，生成当前值与新值的对比材料。
6. 用向量路由给出内容网格、项目单元和关联节点建议。
7. 由策展者检查建议并写明推荐方案，向量结果不能自动写入。
8. 需要时取得 Owner 的冲突决策。
9. 生成最终 Pending Inventory，并导入一个新的密封批次。
10. 展示完整 `batch-review`，等待 Owner 精确确认后原子提交。

## 去重与语义重叠

完全相同的候选可以合并。整理报告必须保留每个来源，不能因为去重而丢失审计信息。

正文不同但含义接近时，只能标记为语义重叠，交给策展者判断。词法向量不具备裁决能力，也不能替代来源证据。

## 冲突材料

同一 Canonical Identity 出现不同值时，至少提供：

- 当前 Active 正文与来源；
- 新候选正文与来源；
- 字段级差异；
- 统一正文 Diff；
- 当前项目权威文件或提交；
- 策展者的推荐方案及理由。

Owner 可以选择：

- 保留当前 Active；
- 用新候选 `supersede` 当前值；
- 重写一个合并候选；
- 使用不同 Canonical Key 保存两个事实，再通过节点关系连接。

冲突决策只允许策展者准备候选。永久写入仍需要新的批次审阅和精确确认。

## 精确批次确认

Runtime 输出 Batch ID 和 Batch Digest 后，Owner 必须原样回复：

```text
确认记忆批次 <batch-id> <exact-digest>
```

确认绑定整份候选列表、顺序、正文、来源和父 Git HEAD。任何一项改变，都必须重新审阅和确认。

## 提交后的工作

策展者检查新 Git 提交、Active Index、节点关系和召回结果，然后重建向量索引。每次新增长期主题或确认误召回时，还要把脱敏查询加入黄金查询集并运行 `vector_memory.py optimize`。不得保存原始私密任务查询，也不得发布质量报告未通过的索引。只有这些检查都通过，批次才算完成。
