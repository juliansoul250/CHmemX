# v0.5.1 版本说明

[English](../v0.5.1.md) · [首页](../../README.zh-CN.md)

v0.5.1 修复维护中断和请求状态恢复。日常 MCP 仍只有 `start`、`recall`、`upload`；TEAM 模式仍需 Owner 精确确认。

## 恢复与请求状态

维护的数据处理已经完成、只剩日志清理时，即使合法的纯 Git 管理操作改变了 HEAD，也能继续完成清理。日志封印、目标文件和暂存字节仍须核验；准备或执行尚未完成时，保留 HEAD 检查，并阻断后续写入。清理已完成事务不会重放数据操作。

归档原文字节不改写。读取和清理归档时，都先核对归档与回执的请求身份；不一致就保留文件并报错。读取时把回执中的提交证明带入状态对账。审批已撤销时返回 `COMMIT_NOT_CURRENT`，即使原先热上传文件的回写失败也能识别。证明来自当前 HEAD 的 Git 历史，不依赖未提交的声明；新版请求还会核对审批记录中的上传 ID。再次审阅不会把已撤销请求重建为新候选。正常停用或替代仍返回 `COMMITTED_NOT_ACTIVE`。

批准与来源停用共用精确回滚：操作失败且尚未提交时，只恢复本次声明的文件，保留无关工作区改动；已成功的提交不会被异常处理撤回。

## 维护成本与诊断

准备计划做一次完整扫描；执行时重新扫描一次，并在本次操作内复用结果。原先两步分别扫描两次和三次。逐文件校验和恢复日志仍保留。待审批次共用本次操作的历史查询，不再逐批启动 Git 历史搜索。

减少重复工作不等于消除维护等待。`--limit` 只限制本批目标数，不限制扫描文件数；协作写入仍需等待操作锁和存储锁，记忆查询仍可用。本版没有实现短锁维护。共享历史查询达到上限时会报 `APPROVAL_HISTORY_LIMIT`，交由操作者检查，不猜测是否曾经提交。

找不到恢复事务时，返回 `TRANSACTION_NOT_FOUND`。原始事件写入中断后，日常状态会提示 `RECONCILIATION_RECOMMENDED`。明确执行维护后，系统核对占位数与实际文件数，修正计数，但不复用事件编号。日常提示只读取元数据，不能证明旧文件从未发生偏差，也不会自动清理或对账。

## 升级

在工具环境安装固定版本，再重启对应 stdio 进程；记忆目录保持独立。升级不改写旧归档或恢复日志。尚未执行的维护计划应重新生成，旧计划可能不再匹配当前字段；已有中断事务按[维护指南](maintenance.md)恢复，不要删除日志。

本版不打开备份、个人模式或云同步，不增加 MCP 写权限，也不调整检索权重。采用其他协议的自定义网关仍须单独验收；更新代码包不等于所有客户端都已升级。
