# v0.5 release notes

[简体中文](zh-CN/v0.5.md) · [Home](../README.md)

v0.5 connects request identity, evidence updates, restore and queue maintenance.
The daily MCP interface remains `start`, `recall`, `upload`; administration stays in the CLI.

## Upload and retry

New request IDs are scoped to the configured source agent, scope and registered project ID.
Global preferences remain global. A subdirectory of one project does not create a separate identity.
Explicit request IDs bind their original input even when the result is an exact-duplicate no-op.
No-op receipts do not occupy hot upload slots or create Active commits.

An existing, verifiable v0.4 request is reused without renaming its ID or rewriting a sealed batch.
Unrecorded legacy no-op requests cannot be reconstructed. An ambiguous missing legacy payload
requires recovery or a new explicit request ID; it is not silently rebound to another project.

Equal text does not imply equal evidence. A changed source for an evidence/state record, or a
changed dependency for a project contract, can create a sourced Pending replacement with a source
diff. It still needs review and confirmation. Unchanged user preferences remain no-ops.

Malformed fact dictionaries defer new candidates with `FACT_CATALOG_REVIEW_REQUIRED`.
Repair and commit the dictionary before sealing their reviews. A damaged canonical store still
fails closed. CLI and MCP use the same structured error fields; missing sources have a domain
error code. Sampling excludes `request_id`, while signatures still bind it. Authenticated requests
consume a nonce even when quarantined; responses identify that consumption.

## Retrieval and restore

Source validity is checked while choosing final results. The reader scans an eligible, bounded
pool to fill valid results; it does not lower relevance thresholds. `needs_review` has a separate
budget, and associations expand from selected usable records. Scan-budget exhaustion is reported.
Freshness checks can share results within one request, never across requests.

Restored stores receive the application's repository-local Git identity and line-ending settings
before checkout. Global Git settings are not changed or copied. Source-project bindings still need
explicit verification on another machine. Restore acceptance includes review, a new commit and recall.

## Queue lifecycle

The [maintenance guide](maintenance.md) covers explicit archive, purge, reconciliation and recovery.
Archives release hot queue slots while retaining history. Purging compressed queue payloads retains
minimal request receipts. Receipt expiry is a separate operation, allowed only after at least 180
days; expired IDs may then be processed as new requests. Nothing expires or deletes automatically.

Plans bind the store, HEAD, current inventory and before/after byte hashes. They show space estimates,
have a 24-hour validity window and require their exact digest. Interrupted preparation or application
blocks further queue mutation until explicit recovery. Unrelated edits cause a recovery conflict;
the tool does not overwrite them.

Canonical Active records, approval history, source projects and external inboxes are not maintenance
targets. Archives, receipts and completed maintenance records are included in opt-in backups. A
backup is refused while a queue transaction is unresolved. Journals support process-interruption
recovery, not recovery from hardware loss; keep separately verified backups if you need that protection.

## Upgrade boundaries

Install into your tool environment and restart its stdio process. Keep the memory store separate.
No schema rewrite of Active memory, automatic cleanup, snapshot enablement, global hooks or cloud
service is part of upgrading. A custom gateway with a different upload protocol needs its own adapter
acceptance; upgrading this package alone does not certify that gateway.

Tests use synthetic stores. Cross-platform CI, installed-wheel tests and frozen ranking regressions
are distinct from real client workflow acceptance. Model weights and held-out answers are not changed
by this release. Historical lessons remain context, not current instructions or permission grants.
